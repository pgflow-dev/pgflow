When a flow worker starts, the worker compiles or verifies its imported flow definition before ready-worker registration or polling. Worker startup is the only supported flow deployment path.

## How It Works

HTTP startup reserves and validates an invocation before initialization. Process workers skip that HTTP reservation. Both paths compile or verify before registering a ready worker:

```text
HTTP only: reserve and validate invocation ID
  -> extract complete shape
  -> compile or verify under the flow lock
  -> HTTP: atomically accept current ID and insert the ready worker row
     process: track the function and insert the worker row
  -> start polling
```

Compilation happens under the flow's advisory lock, so concurrent workers for the same flow serialize safely. If compilation fails, no ready worker row appears and no polling starts. HTTP startup retains its function registration and records the pending invocation as failed with a reason. Process startup still leaves registration unchanged on compilation failure. See [Startup handshake](/deploy/worker-management/#startup-handshake) for reservation, expiry, and retry behavior.

When a worker starts, it:

1. **Extracts the complete flow shape** from the imported TypeScript definition
2. **Compiles the flow if missing** - PostgreSQL creates the flow, steps, and queue from the shape
3. **Verifies the shape if the flow exists** - PostgreSQL compares the worker's shape with the database definition
4. **Registers readiness** - HTTP startup atomically accepts its still-current, unexpired invocation and inserts the worker row; process startup tracks the function and inserts the row. Only then does polling begin.

## Local Development

In local development, startup compilation enables seamless iteration:

1. **No flow exists** - compiles and creates it
2. **Flow exists with same shape** - uses the existing definition
3. **Flow exists with different shape** - **deletes the existing flow and all its run data**, then compiles the new version

The workflow is fully automatic:

1. You change your flow code
2. Edge runtime detects the change and restarts the function
3. pgflow cron triggers the function via HTTP request
4. Worker starts, detects shape mismatch, deletes old flow, compiles new one

<Aside type="caution">
**Warning:** In local development, recompiling **deletes the existing flow, its runs, task state, and queue** before rebuilding it. This is intentional for fast iteration but means you lose all previous runs.
</Aside>

## Production

In production, shape mismatches leave flow data unchanged and cause the worker to **refuse to start**:

- No flow definition, run, or task data is deleted
- No ready worker row is created; HTTP invocation state records the failure
- Worker fails with `FlowShapeMismatchError`
- Resolution: create a new concrete flow version (see [Version Flows](/build/version-flows/))

For breaking pgflow upgrades that change the compilation SQL signature, follow the fenced migration procedure in [Update pgflow](/deploy/update-pgflow/#remove-manual-flow-compilation).

## What is "Flow Shape"?

**Shape comparison detects:**
- step slugs and order;
- step types;
- dependencies;
- `if` and `ifNot` patterns;
- `whenUnmet` and `whenExhausted` behavior.

**Shape comparison does not detect:**
- handler implementation changes;
- TypeScript input or output contract changes;
- tunable retry, delay, and timeout options.
